Цель работы

Изучить влияние модели хранения данных на производительность сложных аналитических запросов, сравнить строковое и колоночное хранение на примере PostgreSQL и ClickHouse, а также определить роль партиционирования и сжатия в OLAP-нагрузках.

Краткая теория

Системы OLTP ориентированы на большое количество коротких транзакций, в которых обычно затрагивается небольшое число строк. Для таких сценариев естественно подходит строковая организация хранения: вся информация об одной записи лежит рядом, поэтому чтение и изменение отдельной сущности выполняется быстро.

Системы OLAP, напротив, выполняют относительно небольшое число сложных аналитических запросов, которые сканируют очень большие объемы данных и обычно используют только часть колонок. В этой ситуации колоночное хранение эффективнее, поскольку сервер читает только нужные столбцы, что заметно сокращает объем I/O и ускоряет агрегации.

Дополнительный выигрыш дают партиционирование и сжатие. Партиционирование позволяет физически не обращаться к нерелевантным диапазонам данных, например к месяцам или годам, которые не входят в условие запроса. Колоночное сжатие особенно эффективно на однотипных значениях внутри отдельной колонки и уменьшает объем данных как на диске, так и при чтении в память.

Ход работы

1. Подготовка окружения

Для сравнения были выбраны две СУБД: PostgreSQL как представитель строкового хранения и ClickHouse как представитель колоночного хранения. В обеих системах используется модель таблицы продаж интернет-магазина.

Запуск контейнера PostgreSQL:

docker run --name pg-oltp -e POSTGRES_PASSWORD=password -p 5432:5432 -d postgres:15

Создание таблицы и генерация тестовых данных в PostgreSQL:

CREATE TABLE sales (

    sale_date DATE,
    amount NUMERIC(10, 2),
    quantity INTEGER,

SELECT

Запуск контейнера ClickHouse:

docker run --name ch-olap -p 8123:8123 -p 9000:9000 -d clickhouse/clickhouse-server

Создание таблицы и генерация данных в ClickHouse:

CREATE TABLE sales (
    product_id UInt32,
    category_id UInt16,
    sale_date Date,
    amount Float32,
    quantity UInt8,
    customer_city String
) ENGINE = MergeTree()
PARTITION BY toYYYYMM(sale_date)
ORDER BY (sale_date, product_id);

INSERT INTO sales
SELECT
    rand() % 1000 + 1,
    rand() % 20 + 1,
    toDate('2025-01-01') + number % 1096,
    rand() % 1000 / 1.0,
    rand() % 5 + 1,
    ['Москва', 'СПб', 'Новосибирск', 'Другой'][(rand() % 4) + 1]
FROM system.numbers
LIMIT 5500000;

Примечание. В данном отчете численные показатели времени и объема прочитанных данных приведены как типовые результаты по методическим указаниям. На другой машине абсолютные значения могут отличаться, но соотношение между строковой и колоночной моделью хранения остается тем же.

2. Сравнение выполнения аналитического запроса

Для сравнения производительности был использован аналитический запрос, считающий суммарную выручку по категориям товаров за 2025 год при фильтрации по городу «Москва».

SELECT
    category_id,
    SUM(amount) AS total_revenue
FROM sales
WHERE
    sale_date BETWEEN '2025-01-01' AND '2025-12-31'
    AND customer_city = 'Москва'
GROUP BY category_id
ORDER BY total_revenue DESC;

Следует отметить, что в исходной формулировке задания был указан диапазон между 2025-01-01 и 2022-12-31, что логически неверно, так как правая граница меньше левой. Для корректного анализа в отчете использован диапазон с 1 января 2025 года по 31 декабря 2025 года.

Запрос для PostgreSQL с анализом плана:

EXPLAIN (ANALYZE, BUFFERS)
SELECT
    category_id,
    SUM(amount) AS total_revenue
FROM sales
WHERE
    sale_date BETWEEN '2025-01-01' AND '2025-12-31'
    AND customer_city = 'Москва'
GROUP BY category_id
ORDER BY total_revenue DESC;

Запрос для ClickHouse:

SELECT
    category_id,
    SUM(amount) AS total_revenue
FROM sales
WHERE
    sale_date BETWEEN '2025-01-01' AND '2025-12-31'
    AND customer_city = 'Москва'
GROUP BY category_id
ORDER BY total_revenue DESC;
СУБД Тип хранения Типовое время Типовой объем прочитанных данных Интерпретация
PostgreSQL Строковое ≈ 1.85 сек ≈ 214 МБ
(27451 страниц по 8 КБ)		 Сервер фактически сканирует почти всю таблицу и читает все поля строк, даже если запросу нужны только дата, город, категория и сумма.
ClickHouse Колоночное ≈ 0.045 сек ≈ 3.9-4.0 МБ Система читает только столбцы sale_date, customer_city, category_id и amount, а остальные данные игнорируются.

Разница объясняется природой хранения. В PostgreSQL значения одной строки лежат вместе, поэтому при полном или почти полном сканировании таблицы считываются не только полезные для запроса атрибуты, но и лишние поля. В ClickHouse каждое поле хранится отдельно, и запрос касается только тех колонок, которые действительно участвуют в фильтрации, группировке и агрегации.

Таким образом, колоночное хранилище позволяет уменьшить объем фактически читаемых данных примерно в 50 раз и получить многократное ускорение выполнения аналитического запроса.

3. Влияние партиционирования

Далее был рассмотрен запрос без фильтра по дате:

SELECT
    category_id,
    SUM(amount) AS total_revenue
FROM sales
WHERE customer_city = 'Москва'
GROUP BY category_id;

В этой ситуации ClickHouse уже не может отбросить лишние месяцы, так как запрос затрагивает весь доступный временной диапазон. Из-за этого число прочитанных партиций, строк и блоков памяти возрастает, а вместе с ним увеличиваются и время выполнения, и пиковое потребление памяти.

Следовательно, партиционирование является не просто способом логической организации таблицы, а важным инструментом ускорения аналитики. Если условие запроса совпадает с ключом партиционирования, сервер физически не обращается к значительной части данных.

4. Оценка сжатия

Размер таблиц предлагается оценивать следующими запросами.

PostgreSQL:

SELECT pg_size_pretty(pg_total_relation_size('sales'));

ClickHouse:

SELECT
    table,
    formatReadableSize(sum(data_compressed_bytes)) AS compressed_size,
    formatReadableSize(sum(data_uncompressed_bytes)) AS uncompressed_size
FROM system.columns
WHERE table = 'sales'
GROUP BY table;
СУБД Типовой размер Комментарий
PostgreSQL ≈ 500-600 МБ Строковое хранение хуже сжимает разнородные данные одной записи и обычно требует большего физического объема.
ClickHouse Сжатый размер обычно в 3-5 раз меньше строкового аналога Однородные значения внутри колонок эффективно кодируются и сжимаются, поэтому выигрывает не только хранение, но и скорость чтения.

Ответы на контрольные вопросы

1. Почему ClickHouse прочитал в разы меньше данных?

ClickHouse использует колоночное хранение и в ходе выполнения запроса читает только те колонки, которые реально нужны: дату продажи, город клиента, категорию товара и сумму продажи. PostgreSQL при строковой организации вынужден читать все поля каждой затронутой строки, даже если часть колонок далее не используется. Поэтому объем ввода-вывода в ClickHouse значительно меньше.

2. Будет ли ClickHouse так же эффективен для запроса SELECT * FROM sales WHERE id = 12345?

Нет, это не типичная сильная сторона колоночной СУБД. Запрос на поиск одной конкретной записи с чтением всех полей ближе к OLTP-нагрузке. Для него строковая СУБД обычно подходит лучше, потому что может быстро найти и прочитать целую строку, тогда как колоночная система оптимизирована прежде всего под массовое сканирование и агрегации.

3. Как повлияет индекс по customer_city в PostgreSQL и нужен ли он в ClickHouse?

В PostgreSQL индекс по customer_city может ускорить выборки, если условие по городу достаточно селективно и возвращает малую долю записей. Однако при широких аналитических запросах с последующей агрегацией по большим диапазонам дат планировщик нередко предпочитает последовательное сканирование, потому что оно дешевле множества случайных обращений к страницам таблицы. В ClickHouse классический B-Tree индекс не нужен: система опирается на сортировку данных, партиционирование, пропуск неактуальных кусков и колоночное чтение. То есть выигрыш достигается другой архитектурой.

4. Модификация запроса: средний чек и количество продаж

Для выполнения задания запрос можно переписать следующим образом:

SELECT
    category_id,
    AVG(amount) AS avg_amount,
    COUNT(*) AS sales_count
FROM sales
WHERE
    sale_date BETWEEN '2025-01-01' AND '2025-12-31'
    AND customer_city = 'Москва'
GROUP BY category_id
ORDER BY avg_amount DESC;

Поведение СУБД при таком запросе концептуально не меняется. PostgreSQL по-прежнему будет читать строковые записи целиком, а ClickHouse ограничится теми же четырьмя нужными колонками: sale_date, customer_city, category_id и amount. Поэтому относительное преимущество колоночного хранения сохранится и для запроса с AVG(amount) и COUNT(*).

Выводы

Выполненный анализ показывает, что для сложных аналитических запросов лучше подходят колоночные СУБД. Их преимущество связано с тем, что при вычислении агрегатов они читают только нужные столбцы, эффективнее используют сжатие и могут исключать неактуальные разделы данных за счет партиционирования.

Строковые СУБД остаются предпочтительными в сценариях OLTP, где доминируют частые точечные вставки, обновления и чтение отдельных записей целиком. В таких задачах колоночная архитектура либо не дает выигрыша, либо может быть менее удобной и менее эффективной.

Партиционирование и сжатие играют ключевую роль в современных аналитических хранилищах. Первое уменьшает объем сканируемых данных за счет физического отсечения ненужных диапазонов, а второе снижает требования к диску и ускоряет передачу данных в память. В совокупности эти механизмы объясняют высокую производительность колоночных СУБД на OLAP-нагрузках.
